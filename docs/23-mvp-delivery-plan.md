# TalentBay: маршрут до работающего MVP

Дата: 2026-10-26. Статус: **предложение для согласования и выбора исполнителя**.
Создание этого плана не запускает реализацию, merge, размещение или платные операции.
Подробные задания: [backlog с постоянными ID](24-mvp-backlog.md).
Фактически выполненное: [execution log](14-mvp-execution.md).

## 1. Цель и граница завершения

Не «набор экранов» и не новый стек. Нужен один понятный продукт:

**найти подходящую вакансию → оценить переезд → войти → подготовить профиль →
передать заявку TalentBay → увидеть, что команда с ней делает → получить следующий шаг.**

Вторая половина продукта — оператор TalentBay: подготовить разрешённый контент,
опубликовать его после проверки, получить заявку, связаться с компанией, представить
кандидата и зафиксировать результат/контакт с кандидатом. Компания может ещё не иметь
аккаунта; это потенциальный B2B-клиент, а не выдуманный пользователь employer-кабинета.

Три разных результата:

| Рубеж | Что должно реально существовать | Чего он не доказывает |
| --- | --- | --- |
| K1: кандидат на независимое ревью | Полный synthetic web/operator путь, миграции, тесты, документация, воспроизводимый локальный запуск | Реальные провайдеры, достоверность данных, готовность публичного запуска |
| K2: проверенный HTTPS preview | Независимое ревью исправлено; допустимый hosting/изолированная БД; настоящие OAuth и Telegram; approved контент; пройдены реальные сценарии | Разрешение переключить production/domain или нанимать от лица компаний |
| K3: контролируемая beta | Отдельное разрешение, миграции/backup/rollback, exact deployment, живые проверки, назначенный оператор | Масштабируемый marketplace, гарантированный найм или готовность Web3 |

Без внешних разрешений автономный исполнитель может дойти до K1 и подготовить K2,
но не должен переименовывать `BLOCKED` в `DONE`. Пустая очередь READY при внешних
блокерах означает отчёт о готовом коде и конкретных зависимостях, а не выполненный K3.

## 3. Что входит в MVP

| Область | Входит | Не является обязательным для первого выпуска |
| --- | --- | --- |
| Candidate | Jobs/detail, источники/даты, relocation estimate, web/TG login, профиль/контакт, review/Apply, прогресс, withdrawal | CV-файлы, чат, social graph, AI ranking |
| TalentBay operations | Очередь, ответственный из действующих ADMIN, ручной контакт/передача/результат, candidate follow-up, безопасное представление данных | Полная CRM, автопродажи, employer self-service |
| Контент | Фиксированный CSV, dry-run, idempotency, review/publish/archive, свежесть, source register | Universal XLSX mapper, массовый crawler, CAPTCHA bypass |
| Relocation | Проверяемые входы/формулы, источники/даты/ограничения, небольшое reviewed покрытие, обновление данных | Бронирование, real-time flight/rent marketplace, персональная налоговая консультация |
| Admin/метрики | Действующие operational screens + маленькие новые workflow, реальные агрегаты и backlog возраст | Полный редизайн админки, BI-платформа, придуманный conversion funnel |
| Эксплуатация | CI, отдельные env/DB, контролируемые миграции, наблюдаемость, backup/restore, release checklist | Kubernetes, микросервисы, новая хостинг-миграция |

Saved пока browser-local. Кандидатский follow-up в v1 — видимый прогресс внутри продукта
и ручной контакт команды по согласованному каналу; автоматическая доставка bot/email
не подразумевается. Если она обязательна для MVP, до старта добавить отдельный delivery
срез с провайдером, согласиями, retries и доказательством доставки, а не один toggle.

Предложение для первого реального пилота: 10–20 разрешённых вакансий и 2–3 проверенных
города, достаточных для полного показа ценности. Это **не согласованный объём и не отмена
исторического пожелания 10–15 городов**. Финальное покрытие выбирает владелец; код не
хардкодит его и поддерживает последующее расширение через данные.

## 4. Архитектурные решения для исполнения

Сохраняются принятые Nuxt/Vue/TypeScript/Nuxt UI/Tailwind/Lucide, Nitro/Node,
Drizzle/PostgreSQL, Vercel/Neon. Lockfile — источник версий. Без переписывания на React,
нового auth framework, FSD-переезда, monorepo, D1 или отдельного TG frontend.

- Страницы собирают UI. Domain-компоненты не ходят в БД.
- `server/api/v1` — тонкий HTTP boundary: session/current role, input/origin/body limits,
  вызов service, безопасный ответ. Services владеют переходами/транзакциями; data access
  остаётся в существующих repo/service границах, без механического рефакторинга всего.
- `shared/types` — явные transport contracts, не замена серверной проверки.
- Новое хранение заявок добавляется backward-compatible миграциями. Старые заявки,
  provider IDs, уникальность Apply и publication invariants сохраняются.
- Журнал обработки TalentBay отделён от employer hiring status. Внутренний просмотр
  **никогда** не ставит `VIEWED`. Публичный progress — безопасная проекция реальных
  событий, а не показ внутренних заметок или автоматически придуманная история.
- Snapshot собирает сервер при новом Apply: минимально нужные профиль/контакт, cover note,
  контекст вакансии/компании и версия подтверждённого disclosure. Старым записям нельзя
  приписывать исторический snapshot из сегодняшнего профиля или новое согласие задним числом.
- Первое представление кандидата — ручная операция человека. Продукт готовит минимальный
  пакет/фиксирует факт и исполнителя; не рассылает данные автоматически, не создаёт
  публичную ссылку на профиль. «Записано оператором» не равно «компания прочитала».
- Withdrawal закрывает последующие in-product действия передачи; уже отправленное вне
  системы невозможно «отменить транзакцией». Для такого случая нужен честный текст и
  ручная процедура, не обещание технического отзыва чужого письма.
- Реальный reviewed relocation dataset проходит полную структурную проверку перед
  записью. LLM не назначает налоговую модель/цены и не переводит DEMO в VERIFIED.
- Наблюдаемость и dashboard используют только измеренные факты. Платёжные, токеновые,
  юридические и инвестиционные поверхности остаются отдельно от SaaS.

## 5. Этапы и зависимости

Задача — проверяемый кусок результата, не обязательно отдельный PR или спринт.
Подробные входы/работы/выходы у 47 задач в [backlog](24-mvp-backlog.md).

| Группа | ID | Результат | Основная зависимость |
| --- | --- | --- | --- |
| A. Основа | A01–A05 | Управляемый PR stack, воспроизводимые проверки, security baseline, acceptance fixtures | Проверенный текущий baseline |
| B. Managed Apply | B01–B09 | Полный путь заявки Candidate → TalentBay → ручная работа → candidate progress | A; policy gate перед реальным sharing |
| C. Вакансии | C01–C05 | Разрешённые данные, удобное ограниченное чтение, поддерживаемое обновление | A; source approval для реальных данных |
| D. Relocation | D01–D06 | Проверенный data workflow, формулы, доверие, обновляемость | A; реальные источники/городской набор |
| E. UX/дизайн | E01–E05 | Цельный web/mobile/TG путь без тупиков и визуальных дефектов | A; B/C/D по нужному сценарию |
| F. Operations | F01–F04 | Метрики работы, runbook оператора/поддержки и восстановления | B/C/D; назначение людей перед beta |
| G. Security/privacy | G01–G05 | Проверка новых границ, PII/миграций/злоупотреблений/публичных обещаний | Соответствующие кодовые срезы |
| R. Независимое ревью | R01–R03 | Другой reviewer проверил exact revision; исправления проверены повторно | Все K1 задачи выполнены или явно исключены |
| H. Preview/release | H01–H05 | Real-provider/native acceptance и контролируемая beta | R; внешние hosting/data/legal/owner gates |

Критический путь к K1:

```text
A01/A02/A03 → B01 + E01 → B02 → B03 → B04 → B05/B06/B07 → B08/B09
                           C02/C03/C04 ───────────────────────┐
                           D02/D03/D05 ───────────────────────┤
                           E02/E03/E04/E05 + F + G ───────────┤
                                                           K1 → R01 → R02 → R03
```

Ветки C01 и D01/D04 (исследование/одобрение данных), A04 и H01 (подготовка окружения)
начинаются рано. Они не должны неделями ждать UI. Реальные загрузки/переключения всё
равно требуют явного разрешения целевой среды.

К K2/K3: `H01 → H02 → H03 → H04 → H05`, с параллельной подготовкой разрешённых данных.
Никакого публичного запуска только потому, что закончилась очередь кодовых задач.

## 6. Пакеты работы вместо выдуманных дат

| Пакет | Что показываем в конце | Приёмка |
| --- | --- | --- |
| P0: подготовка | Baseline/stack, среда, backlog, контракты и эскиз новых workflow | A, B01, E01; понятен следующий READY task |
| P1: полный отклик | Snapshot → заявка → оператор → записанный контакт/передача → прогресс/withdrawal | B02–B09; реальные API/SQL, без внешних адресатов |
| P2: полезное наполнение | Вакансии/источники, полный просмотр списка, обновление и reviewed relocation workflow | C/D; реальные данные отдельно от synthetic acceptance |
| P3: пригодность к использованию | Все ключевые состояния, responsive/a11y, real metrics, операционные инструкции | E/F/G; ноль blocker/high дефектов в основных путях |
| P4: независимая проверка | Отчёт reviewer → исправления → повторные проверки и точный release candidate | R; известны остаточные ограничения |
| P5: реальный preview/beta | Настоящий вход, native TG, оператор и approved данные в целевой среде | H; отдельное разрешение beta |

Это не шесть обязательных двухнедельных спринтов. Можно вести двухнедельные итерации,
но наполнение выбирается по dependency-ready задачам и фактической ёмкости. Старый срок
«3 месяца» не превращается в новый дедлайн. Первые A02/B01/B02 дают калибровку темпа;
после них оценить остаток диапазоном и добавить резерв на defects/review/внешние ожидания.
Модельные токены и минуты генерации не равны инженерным часам и календарной готовности.

S/M/L в backlog — относительная сложность, не обещание часов. Если L нельзя закончить
одной проверяемой поставкой, разделить до работы; не превращать её в скрытую неделю
недоказанного кода. На итоговые сроки влияют также доступы, reviewed данные и ручная
проверка на устройствах. Часы владельца не резервировать автоматически.

## 7. Политика автономного исполнения

### До запуска

Владелец подтверждает границу MVP/исключения и выбирает модель. Исполнитель получает
эти два документа, AGENTS, актуальный execution log и relevant code, не весь архив чата.
Именованные модели/тариф/лимиты проверяются **при выборе**, не назначаются этим планом.
Здесь не создаётся фоновая automation, новый чат или уже запущенный autonomous goal.

### Рабочий цикл

1. Перечитать task, dependencies, current branch/dirty files, source evidence и запреты.
2. Взять один READY срез. Зафиксировать scope и критерий, создать короткую `codex/` ветку.
3. Если нужна новая API/библиотека/provider behavior — сверить официальную документацию;
   не добавлять технологию, когда существующая решает задачу.
4. Реализовать контракт, данные/миграцию, UI states и тесты вместе по риску задачи.
5. Проверить на disposable DB; UI — compiled app плюс скриншоты mobile/wide, API —
   positive/negative/ownership/concurrency сценарии, не только happy path mock.
6. Самопроверка diff, secrets/PII/logs, limits, rollback. Небольшой commit/PR с evidence.
7. Обновить task state и execution log, затем короткий Obsidian current slice. Перейти
   к следующей dependency-ready задаче; не ждать ответа на независимый внешний gate.
8. При завершении очереди выполнить R, затем только разрешённые H. Не объявлять чужой
   ответ/источник/подпись полученными, если их нет.

Первый A01 выбирает integration ref после сверки ancestry. Рекомендуемый путь — один
integration branch от проверенного кумулятивного baseline, topic PR в него и CI для его
PR. Это не автоматический merge в main: сначала исключить production auto-deploy.
Не закрывать старые PR и не переписывать историю «для порядка» без проверенного плана
интеграции. Если выбран другой безопасный путь, записать его до кодовых срезов.

В каждый момент один writer на общий schema/migrations, package/lock, shared contracts
и integration ref. Параллельные исполнители возможны только после отдельного разрешения
на такой запуск и с непересекающимися scope; один координатор интегрирует результат.
Разрешение на Claude CLI для другого проекта сюда не переносится.

В выбранной владельцем двухпроходной схеме первый исполнитель завершает AUTO-задачи
до K1 и оставляет проверяемую передачу. R01/R03 запускаются отдельной reviewer-моделью
после её выбора, а не изображаются тем же исполнителем. Это осознанная точка смены
исполнителя, не забытый остаток работы. H02 и далее следуют после R03 и своих gates.

### Статусы и доска

`BACKLOG → READY → IN_PROGRESS → IN_REVIEW → VERIFIED`; отдельно `BLOCKED` с причиной
и `DEFERRED` по явному scope decision. Для delivery отдельно отмечать merged/deployed/
live-verified. `VERIFIED` task не означает, что feature в production.

Один GitHub Project, представления Backlog/Current/Review/Blocked/Roadmap. Карточки —
repository Issues, не независимые копии текста. Поля: ID, группа, priority, milestone,
status, dependencies, autonomy gate, risk/size, PR, verification SHA. Даты назначать только
после реальной оценки. A05 переносит согласованный backlog, не создаём 47 Issues сейчас.

### Когда остановиться и спросить

- Платный план/лимит/подписка, домен, production, shared DB, real secret rotation.
- Передача реальных профилей/контакт с компаниями от имени проекта.
- Неясные права на источник, legal text, реальный налоговый модельный допуск.
- Новый крупный domain flow/технология/админский редизайн вне согласованных задач.
- Конфликт с чужими изменениями или риск потерять данные/полномочия.
- Два осмысленных подхода не разрешили один blocker: сохранить воспроизведение,
  результаты и точный вопрос; продолжить независимые задачи, не зацикливаться.

Не снижать защиты, не обходить captcha/2FA/plan restrictions, не убирать regression,
не выдавать simulation за native acceptance. Blocking operation не даёт права самовольно
сделать инфраструктурную миграцию. Когда всё оставшееся заблокировано — честная передача.

## 8. Проверки на каждом уровне

Базовый набор — существующие `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`,
`pnpm test:smoke`; tooling, public Playwright и PostgreSQL suite по CI/риску. Не запускать
старый `.env.integration` вслепую; disposable safety assertion и миграции обязательны.
Результаты связаны с точным SHA/командой. Проверки документации не выдаются за runtime QA.

| Сценарий | Обязательный результат |
| --- | --- |
| Гость browser | Jobs/detail/источники/relocation без обязательного TG; понятный переход к входу |
| Новый web candidate | Login → профиль/контакт → preflight → Apply → подтверждение → reload/list/detail |
| Telegram candidate | Настоящий initData/session → тот же путь; back/theme/safe areas/deep link |
| Повторный/параллельный Apply | Одна заявка, понятный 409/retry, нет двойного snapshot/event |
| Два кандидата | Невозможно прочитать/изменить чужую заявку, snapshot, events или contact |
| Оператор | Получить → взять в работу → контакт → подготовить/записать передачу → follow-up |
| Невозможный контакт | Корректная причина/следующий шаг; не фальшивый employer REJECTED |
| Withdrawal во время работы | Сохраняется история, новые share-actions блокируются; прошлое не «отправляется назад» |
| Два оператора/stale UI | Конфликт или идемпотентный replay; не потеря назначения/двойной handoff |
| Контент | CSV preview без записи → draft → review → public → changed re-import скрывает → archive сохраняет заявки |
| Данные переезда | Вход/валюта/период, границы формулы, источники/даты, stale/unsupported и DEMO честно видны |
| Эксплуатация | Request ID/logs без PII, current-role revoke, backup/restore и app/DB rollback проверены раздельно |
| UI | 320/390/768/900/1024/1440, длинный English текст, клавиатура/focus, loading/empty/error/offline |

## 9. Сильная модель после исполнения

Отдельная свежая reviewer-сессия получает исходное задание, baseline/final SHA, diff,
тесты/отчёты и известные ограничения. Самостоятельно воспроизводит сценарии и смотрит
модели данных/authorization/concurrency/migrations; не только читает отчёт исполнителя.
Findings P0/P1 устраняются до release, существенные P2 — по impact и явному решению.
Другой reviewer/model не заменяет реальные Telegram/provider/data проверки и владельца
release. Собственный self-review нельзя называть независимой проверкой.

Модель-исполнитель выбирается по способности удержать task contract и пройти проверки,
стоимости **принятого среза**, числу переделок и доступным лимитам. Пробный bounded срез
до длинного запуска лучше, чем обещание, что самая дешёвая модель реализует всё одинаково.
Security, identity, shared DB и сложные transaction changes не отправляются в производство
по одному самоподтверждению исполнителя.

## 10. Только нерешённые продуктовые/внешние вопросы

Эти ответы не нужны для написания всего независимого кода, но нужны к указанным gates:

1. **Пилот:** подтверждаем малый reviewed набор или в первом релизе обязательны все
   исторические 10–15 городов? Какие города/вакансии приоритетны, кто утверждает источники?
2. **Операции:** кто реально разбирает заявки и общается с кандидатами/компаниями; какой
   рабочий канал и контакт поддержки? Ручного follow-up на старте достаточно?
3. **Передача данных:** какой минимальный кандидатский пакет передаём, нужен ли CV-файл
   уже сейчас? Кто согласует disclosure/Privacy/Terms, хранение и обработку обращений?
4. **Публикация:** какой допустимый hosting бюджет/владелец среды; разрешена ли подготовка
   конкретного isolated preview? Для production/domain/migrations — отдельный go/no-go.
5. **Приёмка:** кто сможет открыть готовый preview и пройти candidate/operator сценарии
   на web и настоящем Telegram? Срок и часы не назначаются планом автоматически.

Выбор таблиц, CSS, веток и конкретных internal endpoint имён не перекладывается на CEO.
Ответы на старые уже решённые вопросы про Web2, Tailwind, Nuxt и managed Apply повторно
не запрашиваются. Новые ответы обновляют только затронутые task/gate, не весь проект.

## 11. После beta, не в бесконечный автономный scope

Server Saved, bot/email delivery, полный admin/CRM, employer cabinet, XLSX mapper,
источники/парсеры по API, дополнительные города/i18n — отдельные backlog extensions
X01–X06. Сначала реальные потребности/метрики и design gate, затем новый план.
Web3/ICO/payment/custody/KYC и гарантирование контрактов этим маршрутом не реализуются.
